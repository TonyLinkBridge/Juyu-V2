# T016 · 首位管理员与新成员开通

> 2026-09-10 当前接入说明：[T059 测试环境配置](../../../docs/setup/T059-test-environment.md)。下文保留各阶段历史记录；公司准入、业务授权与阅读端均已完成本地实现，当前迁移为 0001–0026，真实项目验收仍待完成。

空系统中，首位通过当前 Clerk 会话、公司邮箱和 Slack Workspace 校验、且尚未设置角色的账号自动分配 Admin。首次分配完成后，新的无角色账号默认 Support。二审仍需要另一位 Admin，系统不会为满足二审自动生成第二个管理员。

## 永久初始化边界

迁移 `0005_enrollment` 创建单例 `juyu.initialization` 与按账号唯一的 `juyu.role_enrollments`。迁移遇到已有成员会标记 existing；运行时若发现已有成员或 Clerk 手工设置的合法角色，也会保留已有权限安排，不额外发放 Admin。空值 null、非法角色、大小写错误都拒绝，只有完全未设置 role 的新账号进入默认分配。

初始化只做一次。首位管理员被降权、停用、删除或无法验证，不会把下一位登录者自动提为 Admin。已有成员被移除 role 也不会重新获得默认角色。完成记录不可改写或删除，待处理意图不能更换账号或目标角色。

## 请求与并发

页面和 GET `/api/auth/enrollment` 只检查状态，不写 Clerk。员工开通组件在挂载后自动发送同源 POST，正文只能是空对象；角色与用户 ID 均由服务器确定。不能用查询参数或请求正文选择 Admin。

状态检查采用共享会话锁，真正开通沿用 T015 独占成员锁，在锁内重新核验公司身份。先以数据库事务提交首位账号占位、成员行和开通意图，再调用 Clerk 合并 role。并发首登只能有一位初始 Admin，其他请求会显示等待或稍后核对。初始化完成后再开通后续 Support。

Clerk 登录后的实际后台落点 `/admin` 和 `/admin/sign-in` 都使用相同只读分流：尚需开通时进入 `/help-centre`，完成后刷新员工页；已具备权限者仍须通过原管理员检查。没有查询参数控制的返回网址，也没有从员工开通页自动跳回后台的循环。

## 不确定结果

远端写入错误不代表未执行。数据库保留原账号和意图，之后只核对当前账号是否已具有请求目标角色，不重新发送原角色写入，也不把首次管理员名额转给别人。首位分配仍 pending 时，其他新用户等待。

pending 账号不能绑定业务身份或访问数据库；后台入口和普通成员角色编辑同样拒绝。管理员成员列表标记“等待开通核对”，禁用目标操作，提示该成员本人登录资料库核对原申请。已完成开通会显示“账号已开通”；资料阅读页面仍未移植，不能把账号开通等同于阅读功能完成。

如果原账号失去资格或长期无法核对，需要身份服务管理员确认原远端请求已经结束，再处理原账号。不能自行删除初始化记录、切换占位人、反复写角色，或把等待固定时间、手动设成相同值当作原请求取消证明。核对前后均重新验证当前公司身份。

## 验收与部署限制

本地测试使用一次性 PostgreSQL 和身份供应商替身；没有连接真实 Clerk/Slack/Supabase，没有创建真实账号或变更真实元数据。迁移必须由运维显式执行，应用页面和启动过程不会自动迁移数据库。

真实验收仍需 Clerk 测试项目、具体公司域名、Workspace ID、Supabase/PostgreSQL 测试库及 T015 的两条受限 SQL 连接，使用直连或 session pooling。应在空测试库验证两位合格账号并发首次登录、后续 Support、角色保留、禁用/降权、远端错误及后台回跳。运行中的数据库重复读事务仍受原快照约束。
