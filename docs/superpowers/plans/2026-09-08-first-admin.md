# T016 首位管理员实施计划

沿用已批准的 T016 及本地优先范围，在 Juyu V2 实施，不连接真实账号或部署。

目标：空系统中首位通过公司验证且尚无角色的账号自动 Admin；之后无角色的新账号默认 Support。保留明确的 Clerk 手工角色；已有成员的系统按已初始化迁移，不因管理员消失重新发放 Admin。

设计：新增永久初始化单例和每个账号唯一的角色开通意图。共享身份检查、独占开通写入沿用 T015 同一数据库锁。锁内重新验证当前会话、公司与用户状态。先以事务保留首位账号及意图，再写 Clerk 并核对；不确定状态不重新发送，之后只读取目标账号自身的结果。初始化与意图完成后不可删除或改写。pending 账号被页面、API、数据库统一拦住。

开通通过同源 POST 自动发起；页面 GET、预取和状态读取不分配角色。客户端不能指定 userId 或 role。首次后台登录需要开通时进入相同流程。未完成时显示核对/等待/联系管理员，成功刷新当前页面。后台明确提示二审需要另一位 Admin。

- [x] 先写公司候选人及真实数据库开通测试，复现未实现；实现 0005_enrollment.sql、enrollment/service.ts。覆盖并发首登、后续 Support、角色清空不重授、已有系统、持久 pending、禁止普通 runtime 操作。
- [x] 接入当前身份与同源 POST、状态读取、员工/后台登录分流。测试缺配置和伪造客户端参数、GET 无角色写入。
- [x] 实现自动开通/核对组件与第二位管理员提示；隔离浏览器夹具覆盖成功、等待、不确定、失败，无生产模拟路由。
- [x] 独立复核并修复；运行单元、临时数据库、构建、类型、lint、桌面/手机验收，更新任务清单与真实配置待办。

失败边界：发送前后崩溃不能自动重试远端写入；首位账号资格丧失时保留原占位，不换下一个人。需身份服务管理员确认原请求结束后人工处理。不能以超时或手工设置成相同值本身作为取消证明。

实施补充：实际 Clerk 后台回跳 `/admin` 与登录页共用只读分流。成功账号与未实现的阅读功能分别提示；管理员列表可辨认账号开通 pending。
