## 实现范围

- `/admin/members` 成员列表、三种角色选择、修改前确认、停用/恢复、分页、刷新与最近操作。仅公司已验证的当前管理员可以读取或操作。
- 员工登录入口登记合格成员；每次业务操作从当前 Clerk 会话、公司与 Workspace 校验以及 Backend API 最新角色构造身份，再绑定受限数据库。

- 共享身份锁、独占成员修改锁；禁止自改权限与无变化远端写入；并发交叉降权只能成功一边。

## 复核发现与修复

独立审查发现不匹配核对过早清理 pending 会与远端迟到降权交错；已先复现失败，再修复为保留 pending。无变化 admin→admin 写入同样会造成旧值假确认，现已在创建意图前拒绝。正常员工入口原来未登记成员，现已接入。角色验证与绑定受共享锁保护，成员变更使用独占锁；上下文还须匹配数据库当前观察角色，旧角色上下文回归已通过。完成成员历史增加不可改写触发器，先观察失败再通过完整数据库回归。

复核确认以上重要代码问题关闭。人工恢复说明同时明确：先确认原请求结束，再处理；人工设成相同值或单纯等待不能证明超时请求取消。审查者受其沙箱限制没有独立跑数据库，本记录中的数据库与浏览器证据来自主执行环境实际测试。

## 保留限制与下一项

真实 Clerk、实际公司域名与 Workspace ID、迁移后的 Supabase 测试库和两条受限 SQL 连接尚未配置。不能说真实登录、角色写回、停用或附件访问已联合验收。没有创建真实账号、改真实元数据、运行云端迁移或部署。

必须验证数据库直连或 session pooling；不支持 transaction pooling。运行中的重复读事务保留原快照，新请求按当前角色检查。应用无法阻止 Clerk 控制台直接删改最后管理员；未知角色不会自动得到权限。不确定操作持续 pending 时，需要按成员说明中的人工流程处理。
