## 设计方向

四张图是同一套设计的四个页面，不是四个备选方案。以第一版 JUYU 的品牌、搜索和业务入口为基础，文章使用 GitBook 的目录／正文／小目录结构，参考用户提供的 Notion 层级和 Dynadot 业务入口截图。图内文章、人员、数量均为示例，不是正式资料或已实现功能。

1. 员工首页：固定侧栏，突出搜索、业务入口、常用资料、最近更新与最近浏览。
2. 文章阅读：左侧目录、中间正文、右侧小目录；保留面包屑、收藏、PDF、反馈与上一篇／下一篇。
3. 管理工作台：固定导航、清晰状态筛选、待我审核与直接处理审核入口。
4. 审核详情：文章与审核信息并列，明确提交人、指定审核人和版本；批准与退回可见，批准不等于发布。

## 已发现的实现问题

- admin/loading.tsx 只显示一行文字，后台没有共用 admin/layout.tsx；页面自己的外壳在等待数据后才出现。
- 同页多个服务调用重复取得身份，公司验证含 Clerk 和 Slack 外部访问。
- 成员绑定路径在数据库锁定期间进行外部身份读取；数据库授权上下文也存在多次串行往返。
- 部分后台入口刻意使用整页请求；应在保留服务端权限核验的前提下改善导航。
- 首页直接使用无文章的阅读空状态，没有独立资料入口布局。
- 设置页操作散落在内容容器之外；审核任务缺少直接、醒目的处理入口。

## 确认设计后的实施顺序

1. 对身份核验、数据库连接和查询增加不含敏感信息的分段计时；分别测首次与后续访问。
2. 合并同一请求内重复的身份读取，缩短持锁时间；核对数据库区域后调整函数区域并实测。不得跨用户复用权限结果或关闭公司准入检查。
3. 建立员工与后台共用布局：切换页面保留导航和顶部，只对变化区域显示占位；错误可重试，空数据与读取失败明确区分。
4. 实施四个关键页并统一桌面、手机、深浅色状态。首页空内容时仍有清晰可用入口，但不虚构文章与统计。
5. 推广到搜索、Reference、Q&A、设置；设置说明缩短，细节按需展开，退出放入账号菜单。
6. 验证指定二审人才能操作、批准不自动发布、旧发布版本继续可读，以及搜索／附件／PDF 权限不回退；进行视觉和真实页面性能对比后再发布。

## 本轮实施记录

- 同一个 React 服务端渲染中，共享 session、Clerk user 和公司校验结果。5 个消费者只执行 1 次 Slack userInfo；下一次渲染重新核验；API 操作不跨请求缓存。真实 RSC 渲染测试覆盖撤销与请求隔离。
- 函数 preferredRegion 设置 sin1；本地仅核对数据库主机区域为 ap-southeast-1，未输出连接凭据。生产实际区域与收益待部署确认。
- ScopedDatabase 把四条事务内配置请求合为一条，减少三次往返。角色检测、token、事务、超时和清理均保留。
- 加入可选 JUYU_PERFORMANCE_LOGGING=true 分段计时，仅输出固定阶段、毫秒和结果；阶段为 company.verify、clerk.user、clerk.tokens、slack.userinfo、database.scope。不输出身份、密钥、SQL 或错误正文。没有声称这些阶段可以直接相加，company.verify 包含部分子阶段。
- 首页用一次授权事务取得正式目录、导航、最近修订及个人最近浏览；不虚构热门统计，不返回草稿或无权标题。新功能公告以独立边界读取，不阻塞主内容。
- 后台使用持续保留的导航外壳和内容占位。每个原页面的 server gate 保留。用户明确批准后，外壳只传递一份页面 children，关闭首页搜索仍保留账号退出入口。
- 内容工作台默认表格，区分“处理审核”和“查看审核”。canReview 由服务端当前审核人判断，但最终决定仍由原 API 与数据库检查。
- 首页、目录、翻页、工作台导航使用不提前预取私有内容的 Next Link；不是所有页面的导航都已改完。
- 使用原 JUYU 品牌 PNG；新增页面图标来自 Phosphor，四张图共用布局。审核正文/操作分栏，更多操作收起，手机版表格变成逐项卡片。
