# T060 备份、恢复与回退操作手册

## 当前能力边界

已有本地演练及真实 Supabase 隔离恢复、真实私有媒体恢复证据，见 `docs/verification/2026-09-10-t060-recovery.md`。云端目标为 juyu-recovery-t060（bgrvonvrytlaufityutq）。已执行 Vercel 正式域名回退并恢复当前版本及自动发布。尚未配置自动备份排程、异地加密保管。

本地演练：安装与数据库兼容的 PostgreSQL 客户端，将 pg_dump/pg_restore 放入 PATH 后执行 `npm run test:recovery`。macOS 本次使用 `JUYU_PG_BIN=/opt/homebrew/opt/libpq/bin npm run test:recovery`。命令不会读取 .env，也不接受数据库连接参数；只生成临时数据库和模拟 Storage 服务，结束时删除样例备份及测试实例。

## 一份完整备份包含什么

- `juyu` schema 的表、数据、索引、约束、函数、权限策略和序列。排除短暂的 `request_contexts` 数据，恢复后重新登录建立新请求上下文。
- 与数据库快照对应的附件原始字节和 manifest：文件 ID、所属文章、大小、SHA-256。保留历史版本仍引用的附件和 quarantined 对象；pending 上传先处理完成或取消，已删除对象不应伪装为待恢复文件。
- 所有数据库迁移 SQL、版本与校验值；应用 Git commit、Vercel deployment ID、备份时间及结束时间、数据库版本。
- 运行账号与授权结构、配置名称清单和密钥保管位置。密码、Clerk 密钥不得写进 Git、演练报告或普通日志。Clerk 用户和登录配置在外部服务，不会随着 juyu 数据库恢复。

[Supabase 官方说明](https://supabase.com/docs/guides/platform/backups)：数据库备份不包含 Storage 文件本身，因此仅导出 SQL 不能恢复附件。

## 正式备份前

1. 确认项目 ID、数据库主机、私有 bucket、负责人和备份保存位置。记录最后一次可用备份及可接受的数据损失/恢复时间；目前未承诺 RPO/RTO。
2. 在运维层暂停所有内容写入：编辑、发布、上传、永久删除和清理作业，并等待在途请求结束。当前应用没有已验收的一键维护模式，不能仅通知管理员就宣称数据库与媒体冻结一致。
3. 使用受控运维连接进行数据库导出，不通过员工网页开放备份接口。连接密码从安全环境读取，不放在命令参数；目录权限 0700、文件 0600，并使用加密异地存储。
4. 在冻结窗口导出 `juyu` 的 custom-format archive（排除 request_contexts 数据），从同一不变状态取得 ready/quarantined 文件清单，调用 `backupFiles`。逐个核对大小与哈希，归档迁移 SQL 与 deployment ID。任一附件缺失则整批不能标记为可恢复。
5. 恢复测试通过后才标记备份成功；失败保留上一份可用备份。排程、保留周期和加密存储尚待实际配置。

## 恢复到隔离目标

1. 创建独立数据库与空的私有 bucket；核对目标不是原生产主机。先验证整份 archive、迁移文件及媒体 manifest 的哈希。禁止往生产库直接运行本地测试里的 DROP SCHEMA。
2. 新目标先建立受控迁移所有者、`juyu_runtime` / `juyu_context_issuer` NOLOGIN 能力角色及分别继承的运行登录账号。实际密码单独生成。不能让网页账号继承迁移所有者、superuser 或 BYPASSRLS。本地测试先运行迁移以建立能力角色，再清空自己生成的目标 schema；这不是通用生产恢复命令。
3. 用 pg_restore 的事务及遇错停止模式恢复 schema/data/ACL。确认源/目标所有者映射正确；不存在的所有者或权限报错必须处理，不能忽略继续。恢复媒体到空 bucket；已有同名对象则停止，禁止覆盖不明文件。
4. 比对每张表的数据、序列、迁移校验值、文章与附件关联及实际文件 SHA-256。备份覆盖的数据量不止文章数，审核、历史、设置及成员状态同样要核对。
5. 用隔离部署检查：登录、Admin 内容工作台、Support 普通资料、Ops 内部资料、草稿隐藏、旧正式版本、附件、搜索及 PDF。重新检查 Clerk 当前角色，不能把旧备份里的角色当成当前授权结论。
6. 通过后才计划切换服务配置与部署。记录切换后新增数据的处理方式，并保留原环境；在未处理新增写入前，不能无损退回旧快照。

## 健康检查不是只看绿灯

`/api/health` 只证明网页进程可响应，响应明确标注 `web_process_only`。数据库表比对、迁移检查、受限角色读取及私有文件验证在本地恢复演练中实际执行。线上还需要真实 Clerk 登录、数据库访问、Storage 下载和 PDF 生成；HTTP 200 不代表所有依赖可用，登录重定向页面也不能算业务成功。

## 应用上线回退

1. 上线前记录当前生产 deployment ID / commit、数据库迁移版本及配套备份 ID；选择经过验收的上一版本，不能仅凭“上一条 Git 提交”认定安全。
2. 若只有应用问题且旧版本兼容当前数据库，使用 Vercel 的 Instant Rollback 切回已确认版本；随后核对正式域名实际版本及上述业务健康检查。
3. [Vercel 官方说明](https://vercel.com/docs/instant-rollback)：回退使用先前部署的构建和配置，不会自动采用之后修改的环境变量。密码轮换后尤其要先检查旧部署配置是否仍可用。
4. 应用回退与数据库/媒体恢复分开处理。数据库不兼容时暂停写入，优先修复兼容问题；如必须恢复数据，先在隔离目标完成恢复和增量数据处置，再安排切换。不要将旧迁移 SQL 倒序执行当作 down migration。
5. 保存操作者、时间、原/目标部署 ID、操作结果、健康检查及是否恢复写入的证据。本次已执行真实 Vercel 回退并重新 Promote 原版本，自动分配域名开关已验证开启；未将流量切去恢复数据库。
